# Архитектура интеграции Zenthril и ZenthrilDB

**Статус:** предложение на согласование (Этап A)  
**Версия протокола:** v1 (черновик)  
**Дата:** 2026-10-17  
**Репозиторий:** Zenthril (ветка `main`, HEAD `2476e9b`)

---

## 1. Цель и область действия

Документ описывает безопасный канал взаимодействия между Go-бэкендом мессенджера Zenthril и отдельным процессом собственной СУБД ZenthrilDB (C++23).

**Что этот документ НЕ делает:**
- не заменяет PostgreSQL основным хранилищем;
- не переносит пользовательские данные;
- не меняет протокол сквозного шифрования (E2EE);
- не изменяет существующие SQL-запросы и схему базы;
- не делает ZenthrilDB источником истины для учётных записей, сообщений, ключей или устройств.

Этот документ описывает только инфраструктурный канал и минимальный интерфейс хранения ключ-значение, который ZenthrilDB должна реализовать поверх своего ядра, прежде чем к нему можно будет подключать некритичные данные мессенджера.

## 2. Выводы аудита (база для решения)

### ZenthrilDB (C++23, `zenthrildb-push/`)

Реализовано и покрыто тестами:
- файловый формат `.zdb` с 8 KiB страницами, CRC32, заголовок базы (`DatabaseHeader`);
- `FileManager` — create/open/close, чтение/запись страницы, flush, резерврование идентификатора страницы;
- `BufferManager` — LRU-кэш страниц, `pin()`/`unpin()`, RAII `BufferPageGuard`;
- `PageManager`, `FreePageManager`, `PageDirectory`, `FreePageList` — жизненный цикл пользовательских страниц (с PAGE 4), защита зарезервированных страниц (0–3);
- `MetadataManager` — реестр таблиц на PAGE 1, создание/удаление/переименование/обновление метаданных таблицы;
- WAL — независимый `.wal` файл, LSN, CRC32 на запись, append/replay/flush/truncate/checkpoint, типичные полезные нагрузки (страница, метаданные, транзакция);
- `TransactionManager` — только жизненный цикл транзакции (begin/commit/rollback) с записью границ в WAL, нет MVCC, нет привязки изменений к страницам;
- `LockManager` — shared/exclusive блокировки на уровне таблицы/страницы, таймауты, `LockGuard` RAII, обнаружение deadlock через wait-for graph.

**Не реализовано (подтверждено чтением кода и документации):**
- SQL-движок, парсер, планировщик запросов;
- менеджер строковых записей (record manager) — нет вставки/обновления/удаления по строкам;
- индексы (B+Tree и др.);
- полноценные ACID-транзакции с применением изменений к страницам;
- MVCC, изоляция, снимки;
- применение REDO/UNDO при восстановлении — `UndoRedoRecoveryExecutor` принимает интерфейсы `RedoApplier`/`UndoApplier`, но реальных реализаций нет;
- персистентность `TransactionId` между перезапусками процесса;
- шифрование данных на диске — есть только интерфейсы `IEncryptionProvider`/`IKeyManager` без реализации.

### Zenthril (Go бэкенд)

Все сервисы (`auth`, `message`, `device`, `guild`, `friends`, `user`, `spam` и др.) принимают `*pgxpool.Pool` напрямую (`backend/db/db.go`). Нет абстракции слоя хранения. E2EE — клиентское (X25519-HKDF-SHA256-AES-256-GCM, версия 2), сервер хранит только зашифрованные блобы и конверты ключей получателя.

## 3. Выбранная архитектура: отдельный процесс + IPC

### Обоснование выбора

Рассмотрены варианты:

| Вариант | Плюсы | Минусы | Вердикт |
|---|---|---|---|
| **Отдельный процесс + IPC** | Изоляция сбоев (крах ZenthrilDB не убивает Go-бэкенд), кроссплатформенность, простая отладка, отдельный контейнер в Docker, нет Cgo/ABI рисков | Накладные расходы на сериализацию, управление жизненным циклом процесса | **Выбран** |
| Встраиваемая библиотека через C ABI | Нет накладных расходов IPC | C++ объекты (ссылки на страницы, мьютексы, condition_variable) небезопасны для прямого вызова из Go через Cgo, управление памятью и исключениями сложно, крах C++ убьёт Go-процесс | Отклонён |
| Локальный TCP | Простой протокол | Требует аутентификации и защиты от посторонних процессов на localhost, сложнее управлять правами доступа к сокету | Отклонён (можно вернуться позже) |

**Основной транспорт:**
- **Linux/macOS:** Unix domain socket (AF_UNIX, SOCK_STREAM).
- **Windows:** именованный канал Windows (named pipe, `\\.\pipe\zenthrildb`).

Оба транспорта предоставляют одинаковую семантику потоковых байтов и поддерживают ограничение прав доступа на уровне операционной системы. Два транспорта реализуются через общий интерфейс в Go и общий слой в C++; приложение не знает, какой транспорт используется.

Несколько транспортов одновременно не добавляются без необходимости.

### Границы ответственности

| Компонент | Ответственность |
|---|---|
| Go-бэкенд (Zenthril) | Аутентификация пользователей, autorization, бизнес-логика мессенджера, E2EE, WebSocket, HTTP API, решение о том, какие данные отправлять в ZenthrilDB |
| Процесс ZenthrilDB (C++) | Хранение пар ключ-значение на диске, WAL, буферный кэш, страницы, восстановление после сбоя (по мере реализации ядра), целостность файла `.zdb` |
| IPC-канал | Доставка запросов и ответов, тайм-ауты, обработка обрыва соединения, geen секретов в передаваемых данных |

## 4. Протокол взаимодействия v1

### Транспортный формат

Сообщение передаётся как:

```
[4 байта: длина JSON payload в big-endian uint32][N байт: JSON payload]
```

Максимальный размер одного сообщения: **16 MiB**. Длина проверяется перед выделением буфера, чтобы предотвратить выделение памяти под повреждённое объявление размера.

Формат выбран потому, что:
- JSON одинаково легко парсится в Go (`encoding/json`) и C++ (без внешних зависимостей можно написать минимальный парсер, либо использовать существующий в проекте);
- бинарные значения кодируются в Base64;
- длино-префиксный фрейм позволяет читать сообщения потоково без буферизации по строкам;
- протокол текстового тела упрощает отладку и аудит.

Бинарный протокол с фиксированными полями был отклонён в пользу JSON из-за простоты реализации и тестирования на обеих сторонах без кодогенерации.

### Версия протокола

Каждый запрос и ответ содержит поле `"protocol": 1`. Получение запроса с неподдерживаемой версию возвращает ошибку `ERR_PROTOCOL_VERSION`.

### Операции v1

| Команда | Назначение | Идемпотентная |
|---|---|---|
| `PING` | Проверка доступности процесса | Да |
| `PUT` | Запись значения по ключу (создание или перезапись) | Нет (перезапись существующего ключа) |
| `GET` | Чтение значения по ключу | Да |
| `DELETE` | Удаление значения по ключу | Да (повторное удаление отсутствующего ключа — не ошибка) |
| `EXISTS` | Проверка существования ключа | Да |
| `STATS` | Диагностическая информация без секретов | Да |

### Формат запроса

```json
{
  "protocol": 1,
  "id": "<uuid-строка, уникальный идентификатор запроса>",
  "op": "PUT|GET|DELETE|EXISTS|PING|STATS",
  "key": "<строка, ключ>",
  "value": "<Base64-строка, только для PUT>",
  "ttl_ms": <число, опционально, время жизни записи в миллисекундах>
}
```

**Обязательные поля:** `protocol`, `id`, `op`.

- `key`: строка, длина от 1 до 256 байт (после кодирования UTF-8). Разрешены Unicode буквы, цифры, `_`, `-`, `:`, `/`. Пустой ключ — ошибка `ERR_INVALID_KEY`.
- `value`: для `PUT` — Base64-кодированная строка. Максимальный размер декодированного значения: **1 MiB**. Для остальных операций поле игнорируется.
- `ttl_ms`: опционально. Если указано, запись должна быть удалена по истечении времени. В v1 может быть проигнорировано с возвратом предупреждения в статистике (честно: TTL не гарантируется ядром ZenthrilDB).

### Формат успешного ответа

```json
{
  "protocol": 1,
  "id": "<echo id запроса>",
  "ok": true,
  "op": "<echo op>",
  "value": "<Base64-строка, только для GET>",
  "exists": <bool, только для EXISTS>,
  "ts_ms": <unix-ms времени обработки>
}
```

### Формат ошибки

```json
{
  "protocol": 1,
  "id": "<echo id запроса>",
  "ok": false,
  "op": "<echo op>",
  "error": {
    "code": "ERR_...",
    "message": "<человекочитаемое описание без секретов>"
  }
}
```

### Коды ошибок v1

| Код | Значение | Безопасно повторять |
|---|---|---|
| `ERR_INVALID_REQUEST` | Некорректный JSON или пропущено обязательное поле | Нет |
| `ERR_UNKNOWN_OP` | Неизвестная команда | Нет |
| `ERR_PROTOCOL_VERSION` | Неподдерживаемая версия протокола | Нет |
| `ERR_INVALID_KEY` | Ключ пустой, слишком длинный (>256 байт) или содержит запрещенные символы | Нет |
| `ERR_VALUE_TOO_LARGE` | Значение превышает 1 MiB | Нет |
| `ERR_MESSAGE_TOO_LARGE` | Сообщение превышает 16 MiB | Нет |
| `ERR_KEY_NOT_FOUND` | Ключ отсутствует (для GET/DELETE) | Да |
| `ERR_STORAGE_ERROR` | Ошибка чтения или записи на диск | Да (с осторожностью) |
| `ERR_DISK_FULL` | Недостаточно места на диске | Да |
| `ERR_CORRUPTION` | Обнаружено повреждение файла базы | Нет |
| `ERR_RESOURCE_BUSY` | Ресурс занят другим запросом | Да |
| `ERR_TIMEOUT` | Тайм-аут операции | Да |
| `ERR_INTERNAL` | Внутренняя ошибка процесса | Да |
| `ERR_SHUTTING_DOWN` | Процесс завершает работу | Да |

### Поведение при отсутствующем ключе

- `GET` на отсутствующий ключ → `ERR_KEY_NOT_FOUND` (не пустое значение).
- `DELETE` на отсутствующий ключ → успешный ответ (идемпотентно).
- `EXISTS` на отсутствующий ключ → `{"exists": false}`.

### Тайм-ауты и ограничения ресурсов

| Параметр | Значение v1 |
|---|---|
| Тайм-аут подключения | 5 секунд |
| Тайм-аут операции (запрос-ответ) | 10 секунд |
| Максимальный размер сообщения | 16 MiB |
| Максимальный размер значения | 1 MiB |
| Максимальная длина ключа | 256 байт |
| Максимальное число одновременных соединений | 10 |
| Максимальное число соединений от одного клиента (PID) | 1 |
| Тайм-аут бездействия соединения | 60 секунд |

### Повторные запросы и идемпотентность

**Важно:** ZenthrilDB на текущем этапе **не гарантирует идемпотентности `PUT`**. Если сервер записал данные, но соединение оборвалось до отправки ответа, повторный `PUT` с тем же ключом и значением перезапишет значение (для простого ключ-значения это приемлемо, но для счётчиков или вложений может привести к потере данных).

Операции, которые безопасно повторять после потери соединения: `GET`, `EXISTS`, `DELETE`. `PUT` повторять только если прикладной уровень может перенести перезапись значения.

Если приложению нужна гарантия «выполнено ровно один раз», она должна обеспечиваться на уровне Go (идентификатор запроса `id` передается в ZenthrilDB, но дедупликация на стороне СУБД в v1 не реализована).

## 5. Жизненный цикл процесса и соединений

### Запуск процесса

- ZenthrilDB запускается как **дочерний процесс** Go-бэкенда (или как отдельный контейнер в Docker Compose).
- Путь к файлу базы `.zdb` передаётся аргументом командной строки ZenthrilDB: `zenthrildb --db /var/lib/zenthrildb/app.zdb --pipe \\.\pipe\zenthrildb` (Windows) или `zenthrildb --db /var/lib/zenthrildb/app.zdb --socket /run/zenthrildb/app.sock` (Linux).
- Go-бэкенд **не принимает** путь к файлу базы из пользовательского ввода или HTTP-заголовков. Путь задается только конфигурацией сервера.

### Проверка готовности

После запуска процесса Go-бэкенд подключается к сокету/каналу и отправляет `PING`. Процесс считается готовым только после получения успешного ответа на `PING`. Если ответ не получен в течение 5 секунд, процесс считается неисправным.

### Управление соединениями

- Go-бэкенд поддерживает **одно постоянное соединение** с процессом ZenthrilDB.
- При обрыве соединения Go-бэкенд пытается переподключиться с экспоненциальной задержкой (1с, 2с, 4с, 8с, максимум 30с).
- Количество одновременных соединений от одного процесса Go ограничено одним. Второй процесс Go не может подключиться к тому же экземпляру ZenthrilDB, если он уже обслуживает другого клиента (блокировка на уровне файла базы — см. раздел 7).

### Завершение работы

- При остановке Go-бэкенд закрывает своё соединение и отправляет сигнал завершения процессу ZenthrilDB.
- ZenthrilDB должен завершить текущие операции, сбросить буфер на диск (`flush()`) и закрыть файл `.zdb`.
- Тайм-аут graceful shutdown: 10 секунд. По истечении — принудительное завершение процесса.

### Резервное копирование и восстановление

- Резервная копия: копирование файла `.zdb` и `.wal` во время остановки процесса или через команду `STATS` с информацией о файлах.
- Восстановление: перезапуск процесса с копией файла `.zdb`. Проверка целостности через CRC32 заголовка и страниц при открытии.
- Автоматическая миграция пользовательской базы при старте **не выполняется** без явного режима, резервной копии и проверки результата.

### Исключение одновременного небезопасного открытия

- При открытии файла `.zdb` процесс ZenthrilDB создает файл блокировки `.zdb.lock` в той же директории.
- Второй процесс, пытающийся открыть тот же файл, получает отказ, если блокировка уже удерживается.
- Блокировка освобождается при корректном закрытии процесса или при аварийном завершении (OS освобождает файловые блокировки).

## 6. Модель ошибок и повторных запросов

| Ситуация | Действие клиента (Go) | Безопасность повтора |
|---|---|---|
| `ERR_INVALID_REQUEST` | Прекратить отправку похожих запросов, исправить клиент | Нет |
| `ERR_UNKNOWN_OP` | Проверить версию клиента | Нет |
| `ERR_PROTOCOL_VERSION` | Прервать взаимодействие, обновить клиент или сервер | Нет |
| `ERR_INVALID_KEY` | Исправить ключ на стороне клиента | Нет |
| `ERR_VALUE_TOO_LARGE` | Уменьшить значение или разбить на части | Нет |
| `ERR_KEY_NOT_FOUND` | Обработать как отсутствие данных | Да |
| `ERR_STORAGE_ERROR` | Повторить через 1–2 секунды, максимум 3 попытки | Да |
| `ERR_DISK_FULL` | Сообщить администратору, не повторять без вмешательства | Да |
| `ERR_CORRUPTION` | Переключиться на резервную копию, не использовать поврежденный файл | Нет |
| `ERR_RESOURCE_BUSY` | Повторить с задержкой | Да |
| `ERR_TIMEOUT` | Повторить с экспоненциальной задержкой | Да |
| `ERR_SHUTTING_DOWN` | Подождать перезапуска процесса | Да |
| Обрыв соединения без ответа | Для GET/EXISTS/DELETE — повторить. Для PUT — повторить только если прикладной уровень допускает перезапись | Условно |

## 7. Безопасность

### Права доступа

- **Linux:** Unix domain socket создается с правами `0600` (только владелец процесса Go может подключаться). Файл базы `.zdb` и `.wal` создаются с правами `0600`, директория — `0700`.
- **Windows:** именованный канал создается с DACL, разрешающим доступ только учетной записи, от имени которой запущен Go-бэкенд.

### Границы доверия

- Go-бэкенд и процесс ZenthrilDB запускаются от имени одного пользователя сервиса.
- Между ними нет аутентификации на уровне прикладного протокола (доверяем изоляции ОС и правам доступа к сокету).
- Процесс ZenthrilDB не принимает подключения из сети.

### Ограничения входных данных

- Максимальный размер сообщения 16 MiB, значение 1 MiB, ключ 256 байт — проверяются до выделения буфера.
- Base64-значения декодируются с проверкой длины и алфавита.
- Ключи с путями (`..`, `/`, `\`) не интерпретируются как пути к файлам — ключ — это логический идентификатор, а не путь.

### Логирование

- В логах не записываются значения пар ключ-значение, ключи, содержащие персональные данные, токены, пароли или криптографические ключи.
- Логируются только коды операций, длины значений (без содержимого), коды ошибок и время выполнения.

### Защита от подмены пути

- Путь к файлу `.zdb` задается только в конфигурации сервера при запуске. Пользователь не может изменить его через API.

### Тестовое и рабочее окружение

- Тестовая база использует отдельный файл и отдельный сокет/канал, никогда не пересекается с рабочим.
- В конфигурационных примерах не указываются реальные секреты.

### Сохранение сквозного шифрования

- ZenthrilDB рассматривается исключительно как слой хранения зашифрованных блобов.
- Сервер никогда не передает ключи расшифрования в ZenthrilDB.
- Алгоритмы, KDF, salt, info, форматы криптографических конвертов и правила ratchet не изменяются.

## 8. Недостающие возможности ZenthrilDB (требуют доработки ядра перед использованием)

1. **Менеджер строковых записей (record manager):** операции `PUT`/`GET`/`DELETE` в протоколе v1 не могут быть реализованы поверх текущего `writePage` без формата хранения пар ключ-значение на страницах. Необходимо разработать минимальный формат записи (ключ, значение, флаг удаления, версия) и отображение ключа на страницу.
2. **Транзакции с применением к страницам:** текущий `TransactionManager` записывает только границы в WAL, но не связывает изменения страниц с транзакцией.
3. **Восстановление после сбоя:** `RecoveryEngine` только анализирует WAL, но не применяет redo/undo к страницам. Долгосрочная сохранность данных после аварийного завершения не подтверждена.
4. **Индексы:** поиск по ключу в v1 может быть линейным сканированием страниц (для прототипа приемлемо, для production — нет).
5. **Персистентность TransactionId:** счетчик сбрасывается при перезапуске.

|---|---|---|

| **G — Оценка результатов** | Надёжность, производительность, документация, решение о дальнейшей интеграции | Отчёт с воспроизводимыми измерениями |

## 10. Условия отказа и возврата

- Если на этапе B или C ZenthrilDB не подтверждает сохранность данных после аварийного завершения, интеграция приостанавливается. PostgreSQL остаётся единственным хранилищем.
- Если на этапе E выявляются расхождения между PostgreSQL и ZenthrilDB, запись в ZenthrilDB отключается, расхождения исследуются.
- Возврат к предыдущему состоянию всегда возможен: Go-бэкенд继续 пишет в PostgreSQL независимо от состояния ZenthrilDB.

## CRY-203 — Persistent DH ratchet private key strategy

**Приоритет:** HIGH
**Статус:** требует решения владельца протокола
**Зависит от:** CRY-101 (нормативная схема должна быть зафиксирована первой)

### Проблема

Функция `serializePairwiseSession` не сохраняет `dhSendPrivate`.
При восстановлении `restorePairwiseSession` устанавливает
`new Uint8Array(32)`, то есть нули. Проверено, что `performDHRatchetTurn`
fail-closed и отклоняет нулевой приватный ключ, поэтому DH-шаг ратчета после
перезапуска клиента невозможен.

Файл: `client/src/features/e2ee/pairwiseSession.ts`, функции
`serializePairwiseSession`, `restorePairwiseSession`, `performDHRatchetTurn`.

### Что уже сделано

- Устранено обнуление ключа у инициатора: `initializeDHRatchet` теперь копирует
  ключевой материал вместо сохранения ссылки на обнуляемый буфер.
- Добавлена проверка `hasUsableDHPrivateKey` с fail-closed поведением.

Остаётся нерешённым именно вопрос хранения приватного DH-ключа между запусками.

### Варианты

**A. Шифрованное локальное хранение.**
Пре-/постусловное хранение `dhSendPrivate` рядом с остальным состоянием сессии.

Требует: определить ключ шифрования и его источник; определить, чем
шифровать, если сам ключ должен где-то храниться; определить поведение при
отсутствии ключа.

Затрагивает: `pairwiseSession.ts` (сериализация), `deviceKeyStore.ts`,
возможно `crypto/index.ts` для envelope-шифрования.

**B. Повторный bootstrap (re-bootstrap).**
Считать, что приватный DH-ключ не восстанавливается, и после перезапуска
переустанавливать сессию через X3DH.

Требует: определить момент переустановки; определить, требуется ли
предупреждение пользователя; определить поведение для сессий, где bootstrap
невозможен (удалённый пользователь офлайн).

Затрагивает: `pairwiseSession.ts`, код вызывающий `restorePairwiseSession`,
потенциально UI-информирование.

**C. Протокол восстановления сессии.**
Отдельный обмен с пиром, позволяющий восстановить DH-состояние без хранения
приватного ключа.

Требует: спроектировать обмен; определить аутентификацию обмена; определить,
как избежать расширения окна компрометации.

Затрагивает: `pairwiseSession.ts`, `messageEnvelopes.ts`, возможно новый тип
конверта и миграция схемы.

**D. Иное технически обоснованное решение**, не перечисленное выше.

### Данные, необходимые для решения

1. Допустимо ли хранить приватные DH-ключи на диске в принципе, с учётом
   модели угроз Zenthril.
2. Какое максимальное время жизни сессии допустимо без возможности DH-шага.
3. Требуется ли непрерывность переписки через перезапуск или допустима
   переустановка сессии с уведомлением.
4. Есть ли в продукте другие уже принятые решения по хранению ключевого
   материала, которые задают прецедент.

## SEC-401 — Trusted proxy IP extraction

**Приоритет:** HIGH
**Статус:** требует решения владельца по топологии развёртывания
**Зависит от:** нет
**Исправление в этом раунде НЕ выполнялось** — этап был документационным.

### Текущее поведение

`backend/security/guard.go`, функция `extractIP` (строка 185):

```go
if xff := r.Header.Get("X-Forwarded-For"); xff != "" {
    parts := strings.Split(xff, ",")
    if ip := strings.TrimSpace(parts[0]); ip != "" {
        return ip
    }
}
if xri := r.Header.Get("X-Real-IP"); xri != "" {
    return strings.TrimSpace(xri)
}
```

Значение берётся из заголовков, которые полностью контролирует клиент, и
используется без сверки с `RemoteAddr` и без проверки доверенного прокси.

Комментарий в коде (`guard.go:186-190`) утверждает, что значение применяется
«только для логирования и мягких блокировок» и «не влияет на решения контроля
доступа». **Это утверждение не соответствует фактическим вызовам** (см. ниже).

### Затронутые защиты и точная цепочка вызовов

| Защита | Файл:строка | Использование значения |
|---|---|---|
| `Guard.IPRateLimit` | `security/guard.go:36` | ключи `security:ip_block:<ip>`, `security:ip_rps:<ip>` |
| `Guard.BruteForceProtect` | `security/guard.go:67` | ключи `security:bf_block:<ip>`, `security:bf_fails:<ip>` |
| `Guard.AuthRateLimit` | `security/guard.go:128-129` | ключ `security:rl:<scope>:<ip>` |
| `Guard.LogSecurityEvent` | `security/guard.go` | колонка `security_log.ip_address` |

`AuthRateLimit` ограничивает `/register` (10 в час), `/refresh` и `/logout`
(30 в минуту) — то есть защита, добавленная в раунде `44e6e0b`, обходится тем же
способом.

### Влияние

1. **Обход защиты от подбора паролей.** Счётчик 401 ведётся по извлечённому «IP».
   Ротация значения заголовка даёт неограниченное число попыток входа,
   credential stuffing не ограничен.
2. **Обход лимитов регистрации.** Массовая регистрация аккаунтов не
   ограничивается.
3. **Отравление `security_log`.** В журнал попадает значение из заголовка.

### Независимая проблема того же класса

`backend/moderation/middleware.go:25` вызывает
`moderation.ExtractRealIP(headers, r.RemoteAddr)`, который доверяет **восьми**
заголовкам: `CF-Connecting-IP`, `True-Client-IP`, `X-Real-IP`,
`X-Forwarded-For`, `X-Client-IP`, `X-Cluster-Client-IP`, `Forwarded-For`,
`Forwarded`. Результат записывается в `user_ip_log`. Обнаружено отдельно от
`security/guard.go`; затрагивает наблюдаемость и потенциальные решения по IP.

### Требуемая концепция конфигурации

Доверие к прокси-заголовкам должно быть **включаемым**, а не включённым по
умолчанию:

| Параметр | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `TRUSTED_PROXY_HOPS` | целое | `0` | число доверенных обратных прокси, дописывающих реальный адрес в `X-Forwarded-For` |

- При `0` используется **только** `RemoteAddr`.
- При `N > 0` значение берётся из `X-Forwarded-For` с позиции
  `len(parts) - N`; при недостатке элементов применяется `RemoteAddr`.
- Отрицательное значение должно приводиться к `0`, чтобы ошибка конфигурации
  не включала доверие.

### Требуемые тесты

1. При значении по умолчанию заголовок `X-Forwarded-For` игнорируется, ключ
   строится из `RemoteAddr`.
2. При значении `0` ротация заголовка не позволяет обойти лимит.
3. При `N = 1` и `N = 2` выбирается корректная позиция в цепочке прокси.
4. При `N = 2` и длине XFF меньше `N` применяется `RemoteAddr`.
5. Отрицательное значение конфигурации приводится к `0`.
6. `X-Real-IP` учитывается только при включённом доверии.

### Данные, необходимые для решения

1. Есть ли в штатном развёртывании обратный прокси перед сервисом
   (`deployments/docker-compose.prod.yml`, ingress, CDN, Cloudflare).
2. Сколько прокси в цепочке.
3. Должен ли `security_log.ip_address` хранить реальный адрес клиента или адрес
   прокси.
4. Допустимо ли ужесточение поведения без смягчения: у клиентов, обращающихся
   напрямую, после исправления ключи лимитов изменятся.

## FEAT-AVATAR-001 — Server-side avatar storage

**Приоритет:** MEDIUM
**Статус:** требует продуктового и архитектурного решения
**Зависит от:** нет

### Проблема

Файл: `client/src/components/ProfileModal.tsx:92-97`.

Аватар читается через `FileReader` в data URL и хранится только локально в
состоянии профиля. Проверено:

- в `client/src/api/index.ts` нет API загрузки;
- в `backend/main.go` нет маршрута upload и нет обработки multipart;
- лимит 5 МБ проверяется только на клиенте.

Последствия:

1. Аватар не синхронизируется между устройствами пользователя.
2. Проверка размера на клиенте не является защитой сервера.
3. При выборе файла близкого к 5 МБ base64 составит около 6,7 МБ, что с высокой
   вероятностью превышает квоту localStorage. Обработки `QuotaExceededError`
   в компоненте не найдено.

### Пункты для исследования

| Область | Что определить |
|---|---|
| Endpoint | метод, путь, размещение в группе `/api/v1` с `Middleware` |
| Авторизация | подтвердить, что загрузка привязана к текущему пользователю, а не к произвольному `userId` |
| Валидация типа | проверка MIME по содержимому, а не по расширению и не по заголовку от клиента |
| Декодирование | фактическая попытка декодировать изображение, чтобы исключить содержимое, не являющееся изображением |
| Максимальный размер | **ограничение на сервере**, независимое от клиентского |
| Размеры изображения | допустимые границы ширины и высены; защита от decompression bomb |
| Хранилище | файловая система, объектное хранилище или хранение в PostgreSQL |
| Имя файла | генерируемое сервером, не зависящее от имени пользователя; предотвращение path traversal |
| Замена | поведение при загрузке нового аватара поверх существующего |
| Удаление | удаление аватара и его файла |
| Кэш | заголовки кэширования и отзыва кэша после замены |
| Rate limit | ограничение частоты загрузок на пользователя |
| Abuse | защита от загрузки файлов, не являющихся изображениями, и от переполнения диска |
| Квота | максимальный суммарный объём аватаров на пользователя |

### Ограничение

Реализация не начинается до завершения анализа архитектуры. До этого
состояние фиксируется как BROKEN в матрице покрытия.

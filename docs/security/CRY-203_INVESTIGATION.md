# CRY-203 — Investigation: DH private key persistence and restart behaviour

**Статус:** расследование. Реализация CRY-203 **не выполнялась**.
**Дата:** 01.10.2026
**Ревизия:** `82bbb0a`
**Связанные документы:** `E2EE_ARCHITECTURE_AUDIT.md`, `OPEN_TASKS.md`

## 1. Scope

Исследование по разделам 9–11 задания: почему `dhSendPrivate` не сохраняется,
является ли это сознательным решением, что фактически происходит после
перезапуска, и какова реальная величина ограничения.

Поведение после перезапуска проверено тестами, а не только чтением кода.

## 2. Почему `dhSendPrivate` не сохраняется

Установлено по коду: **осознанного решения нет.**

| Факт | Место |
|---|---|
| Поле отсутствует в `StoredPairwiseSession` | `types.ts` |
| `serializePairwiseSession` его не записывает | `pairwiseSession.ts:96-110` |
| В комментарии сказано «persisted session format carries no dhSendPrivate field» | `pairwiseSession.ts:435` |
| Объяснения *почему* формат такой — нет | — |

Хронология по истории коммитов:

1. Изначально `initializeDHRatchet` сохранял **ссылку** на буфер приватного
   DH-ключа, а `initiatePairwiseSession` обнулял этот буфер в блоке `finally`.
   То есть у инициатора `dhSendPrivate` был нулевым с момента создания сессии.
2. Fail-closed проверка `hasUsableDHPrivateKey` добавлена позже как **исправление
   уязвимости** (коммит `50d9a0b`), потому что X25519 клампит нулевой скаляр в
   публично известную константу.
3. Отсутствие поля в формате — незавершённая функциональность, а не требование
   безопасности. Иначе проверка fail-closed была бы не нужна: при осознанном
   решении не хранить ключ отсутствие ключа и было бы ожидаемым состоянием.

**Вывод:** это недоработка, закрытая предохранителем. Сохранять ключ безопасно
можно в том же хранилище, где уже лежат более чувствительные материалы.

## 3. Можно ли безопасно сохранять приватный DH-ключ

Ключевой факт: **бандл уже хранит материал того же класса чувствительности.**

| Материал | Чувствительность | Где хранится |
|---|---|---|
| `identityDHKey.secretKey` | приватный X25519 | бандл → keyring |
| `signedPreKey.secretKey` | приватный X25519 | бандл → keyring |
| `oneTimePreKeys[*].secretKey` | приватные X25519 | бандл → keyring |
| `rootKey` | корень Double Ratchet | бандл → keyring |
| `sendChainKey`, `receiveChainKey` | цепочки, дают message keys | бандл → keyring |
| `dhSendPrivate` | приватный X25519 для DH-шага | **не хранится** |

Извлечение приватного ключа из сохранённого `rootKey` невозможно, но
`sendChainKey` напрямую определяет `messageKey`. То есть злоумышленник, получив
доступ к бандлу, уже может читать исходящие сообщения.

**Следствие:** добавление `dhSendPrivate` в персистированное представление не
создаёт нового класса экспозиции. Ключ должен попасть в то же зашифрованное
хранилище ОС, что и остальные поля.

Требования к реализации, если вариант будет выбран:

1. Не расширять `localStorageAdapter`. Он помечен `"insecure-localstorage"`
   (`deviceKeyStore.ts:177`).
2. Использовать существующий путь `store_device_key_bundle`.
3. Обновить валидацию в `deviceKeyStore.ts`, где перечисляются допустимые поля.
4. Учесть, что `validateState` уже проверяет длину `dhSendPrivate`; нужен ещё
   тест на нулевое значение при восстановлении.

## 4. Что происходит после перезапуска — доказано тестами

Десять тестов в `client/src/features/e2ee/pairwiseSession.restart.test.ts`
моделируют перезапуск циклом `serializePairwiseSession` → `restorePairwiseSession`,
что точно воспроизводит границу персистентности.

| Аспект | Результат | Статус |
|---|---|---|
| Восстановление `rootKey` | идентичен | **работает** |
| Восстановление цепочек | идентичны | **работает** |
| Восстановление счётчиков | идентичны | **работает** |
| Исходящие после перезапуска | ключ совпадает у отправителя и получателя | **работает** |
| Входящие после перезапуска | ключ совпадает | **работает** |
| Ответное направление | работает на восстановленной цепочке | **работает** |
| Одновременный перезапуск обеих сторон | сессия сохраняется | **работает** |
| Skipped message keys | переживают перезапуск, освобождаются один раз | **работает** |
| Защита от replay | потреблённый счётчик отвергается | **работает** |
| Откат цепочки | не происходит | **работает** |
| Идентичность сессии, привязка к пиру, версия | сохраняются | **работает** |
| **`dhSendPublic` стабилен** | не меняется, пир не видит ложной ротации | **работает** |
| **DH-шаг** | **fail-closed: исключение** | **ограничение** |

**Вывод: обычный обмен сообщениями после перезапуска не ломается.** Ограничение
касается только DH-шага.

## 5. Почему ограничение пока не проявляется

Установлено по коду: **отправитель никогда не выполняет DH-шаг.**

| Путь | Вызов `performDHRatchetTurn` |
|---|---|
| Отправка, `messageEnvelopes.ts:59` | нет — только `nextSendMessageKey` |
| Отправка, `messageEnvelopes.ts:74` | нет — отправляется неизменённый `state.dhSendPublic` |
| Приём, `messageEnvelopes.ts:116-118` | **да**, если `envelope.dhPublicKey` отличается от `dhRecvPublic` |

`dhSendPublic` меняется только в `dhRatchetTurn` (`crypto/ratchet.ts:59`), куда
попадают исключительно через приём. Никакого активного продвижения DH-ратчета
по инициативе отправителя в коде нет.

Практические следствия:

1. Значение `dh_public_key` в конвертах остаётся постоянным в пределах сессии.
2. Перезапуск не меняет `dhSendPublic`, поэтому пир не инициирует ротацию —
   это подтверждено тестом.
3. DH-шаг возникает только когда пир ранее выполнил приёмную ротацию. Такое
   возможно лишь в цепочке A→B→A, и оно требует, чтобы у A уже была
   восстановленная сессия с ключом.

**Следствие для оценки безопасности:** в текущей реализации
post-compromise security за счёт DH-шага практически не работает, потому что
шаг почти никогда не происходит. Это отдельная архитектурная находка, не
зависящая от CRY-203.

## 9. SEC-401: незакрытая часть

`backend/security/guard.go` исправлен (коммит `fff6ff7`), покрыт 19 тестами.

`backend/moderation/middleware.go:25` вызывает `moderation.ExtractRealIP`,
который доверяет восьми заголовкам и пишет результат в `user_ip_log`.
Исправление **не выполнялось** в этом раунде: требуется то же подключение
`TRUSTED_PROXY_HOPS`, а изменение затрагивает сигнатуру публичной функции и
проверку хранения IP-адресов, то есть отдельный логически завершённый блок.

**Риск до исправления:** значения из заголовков попадают в `user_ip_log` и могут
влиять на решения по IP-адресам. На rate limiting и brute-force защиту это не
влияет, поскольку они используют `security.Guard`.

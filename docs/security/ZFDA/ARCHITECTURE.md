# ZFDA ARCHITECTURE — Целевая архитектура защиты Zenthril

## Обзор

Архитектура ZFDA встроена в каждый компонент Zenthril. Защита не является отдельным слоем — она пронизывает все уровни приложения.

## Компоненты и их модели угроз

| Компонент | Модель угроз | Основные защиты |
|-----------|-------------|-----------------|
| Backend HTTP API (Go, Chi) | Инъекции, IDOR, CSRF, brute-force, credential stuffing | Rate limiting, brute-force защита, валидация входа, JWT HS256 |
| WebSocket шлюз (Gorilla) | CSWSH, flooding, replay, несанкционированный доступ | One-time тикеты, Origin валидация, лимиты сообщений, проверка доступа к каналам |
| PostgreSQL | SQL injection, утечка данных, несанкционированный доступ | Параметризованные запросы, RBAC, безопасная конфигурация |
| Redis | Утечка токенов, отказ в обслуживании | Изоляция в Docker сети, аутентификация |
| Tauri клиент (React, TypeScript) | XSS, кража ключей, compromised device | OS keychain, память процесса вместо localStorage, валидация конвертов |
| E2EE криптография (X25519, HKDF, AES-GCM) | Компрометация ключей, replay, несовместимость реализаций | Сервер не получает приватные ключи, AAD конверт, fail-closed |

## Взаимодействие десяти уровней

Уровни взаимодействуют как единая система:

1. **Perimeter (1)** фильтрует входящий трафик перед доходом до приложения.
2. **Identity (2)** аутентифицирует пользователя и выдает токены.
3. **Device (3)** идентифицирует устройство и ограничивает сессии.
4. **Application (4)** валидирует каждый запрос и бизнес-операцию.
5. **Network (5)** шифрует трафик и сегментирует сервисы.
6. **Server (6)** жестко настраивает хостинг и изоляцию процессов.
7. **Cryptographic (7)** защищает данные на уровне криптографии (E2EE).
8. **Data (8)** контролирует доступ к данным и шифрует при покое.
9. **Detection (9)** обнаруживает аномалии и угрозы.
10. **Recovery (10)** восстанавливает систему после инцидента.

Каждый уровень имеет собственные независимые проверки. Компрометация одного уровня не открывает доступ ко всей системе.

## Границы доверия

1. Клиент → Backend HTTP API (JWT + Origin)
2. Клиент → WebSocket (one-time тикет + Origin)
3. Backend → PostgreSQL (параметризованные запросы, пользователь БД с ограниченными правами)
4. Backend → Redis (изолированная сеть, отдельные ключи)
5. Клиент → локальное хранилище ключей (OS keychain)
6. Federation boundary (отключена по умолчанию, fail-closed)

## Принципы

- **Defense in Depth**: каждый компонент имеет собственную защиту.
- **Zero Trust**: никто не доверяется по умолчанию.
- **Least Privilege**: минимальные необходимые права.
- **Separation of Duties**: криптографические операции изолированы от бизнес-логики.
- **Compartmentalization**: база данных не доступна всем компонентам напрямую.
- **Fail Secure**: при ошибке система закрывает доступ.
- **Assume Breach**: система costruится с учетом компрометации любого компонента.
- **Secure by Default**: безопасные настройки по умолчанию.
- **Defense Against Lateral Movement**: компрометация одного секрета не дает полный контроль.
- **Recovery by Design**: система способна безопасно восстанавливаться.

## Отказоустойчивость

- Graceful shutdown WebSocket и HTTP сервера.
- Readiness проверки зависимостей (PostgreSQL, Redis).
- Produktion конфигурация валидируется fail-closed.
- Отсутствие критических секретов в исходном коде (isPlaceholderSecret).

## 2. Требования к управлению секретами

- ✅ Никаких секретов в Git
- ✅ Никаких секретов в Docker images (.dockerignore настроен)
- ✅ Никаких секретов в логах (логи не содержат значений секретов)
- ⚠️ Нет слабых fallback-ключей (необходимо убрать значения по умолчанию в .env.example)
- ⚠️ Нет одинаковых ключей для независимых компонентов (нужно разделить JWT_SECRET и другие)
- ⚠️ Разделение ключей по назначению (требуется реализация)
- ⚠️ Безопасная ротация (требуется документирование)
- ⚠️ Документированная процедура отзыва (требуется создание)

## 3. Стратегия ротации JWT ключей

### Проблема
При компрометации JWT_SECRET все действующие access tokens остаются валидными до истечения срока.

### Решение

1. **Двухуровневая система ключей:**
   - `JWT_SIGNING_KEY` — для подписи новых токенов
   - `JWT_VERIFICATION_KEYS` — список ключей для валидации (включает старые для плавной ротации)

2. **Процедура ротации:**
   ```
   1. Добавить новый JWT_SIGNING_KEY в secret manager
   2. Добавить старый ключ в JWT_VERIFICATION_KEYS (для валидации существующих токенов)
   3. Развернуть обновлённый бэкенд
   4. Подождать истечения всех старых access tokens (max 15 минут)
   5. Удалить старый ключ из JWT_VERIFICATION_KEYS
   6. Развернуть бэкенд без старого ключа
   ```

3. **Refresh token ротация:**
   - Access tokens: 15 минут TTL (короткое время жизни минимизирует ущерб)
   - Refresh tokens: хранение в Redis с rotation (GETDEL), replay detection
   - При компрометации refresh token: отзыв всех активных refresh токенов пользователя

## 4. Стратегия ротации TOTP encryption keys

### Проблема
TOTP секреты зашифрованы AES-256-GCM. При компрометации ключа шифрования все TOTP секреты могут быть расшифрованы.

### Решение

1. **Версионирование ключей:**
   - Каждый зашифрованный TOTP секрет хранит идентификатор ключа (key_id)
   - При ротации: новый ключ получает новый key_id, старый ключ сохраняется для дешифрования существующих секретов

2. **Процедура ротации:**
   ```
   1. Сгенерировать новый TOTP_ENCRYPTION_KEY_v2
   2. Сохранить оба ключа (v1 и v2) в secret manager
   3. При дешифровании: использовать key_id для выбора ключа
   4. При следующем входе пользователя: перезашифровать его TOTP секрет новым ключом (v2)
   5. После перешифрования всех пользователей: удалить старый ключ v1
   ```

## 5. Процедура отзыва при компрометации

| Сценарий | Действия |
|----------|----------|
| Компрометация JWT_SECRET | 1. Ротировать ключ (см. выше)<br>2. Отозвать все refresh токены в Redis<br>3. Заставить всех пользователей повторно войти |
| Компрометация refresh token конкретного пользователя | 1. Отозвать все refresh токены пользователя через `/api/v1/auth/logout-all`<br>2. Пользователь должен повторно войти |
| Компрометация устройства (E2EE ключи) | 1. Отозвать устройство через управление устройствами<br>2. Регенерировать ключевые связки на устройстве<br>3. Уведомить контакты о смене ключей |
| Компрометация сервера (база данных) | 1. Ротировать все секреты (JWT, DB, Redis, TOTP)<br>2. Восстановить из чистого бэкапа<br>3. Принудительный сброс всех сессий |

## 6. Рекомендуемый secret manager

Для production развёртывания рекомендуется использовать один из:
- **HashiCorp Vault** —自我管理, полный контроль
- **AWS Secrets Manager** — если инфраструктура в AWS
- **Docker Secrets** — для Docker Swarm развёртываний
- **Kubernetes Secrets** — для K8s развёртываний (с шифрованием etcd)

Секреты должны Inject'иться в контейнеры через переменные окружения из secret manager, а не из .env файлов.

# ZFDA 1.3 — Incident Response Plan (План реагирования на инциденты)

## 1. Типы инцидентов

| Тип инцидента | Примеры | Серьезность |
|---------------|---------|-------------|
| Компрометация секрета | Утечка JWT_SECRET, POSTGRES_PASSWORD, REDIS_PASSWORD | Критический |
| Уязвимость в зависимости | CVE в npm пакете или Go модуле | Высокий |
| Несанкционированный доступ | Злоумышленник получил доступ к аккаунту пользователя | Высокий |
| DDoS атака | Массовые запросы к API или WebSocket | Средний |
| Утечка данных | Экспорт пользовательских данных без'autorization | Критический |
| Недоступность сервиса | Бэкенд, БД или Redis не отвечают | Высокий |
| Подозрительная активность | Аномальное количество auth failures, необычные паттерны запросов | Средний |

## 3. Процедура реагирования

### Фаза 1: Обнаружение (Detection)

| Источник | Что мониторить | Инструмент |
|----------|---------------|------------|
| Метрики защиты | `zenthril_ws_rate_limit_hits_total`, `zenthril_readiness_failures_total` | Prometheus + Alertmanager |
| Логи аутентификации | auth failures, токен replay, отказы в доступе | Zentralized logging |
| Внешние отчёты | Сообщения об уязвимостях | Email (ax1plee@gmail.com), GitHub Issues |
| Системные метрики | CPU, Memory, Disk, Network | Node Exporter + Prometheus |

### Фаза 2: Оценка (Assessment)

```
1. Подтвердить инцидент
2. Определить серьезность (по таблице выше)
3. Оценить масштаб (сколько пользователей затронуто, какие данные)
4. Определить критичность для бизнеса
5. Назначить ответственного
```

### Фаза 3: Сдерживание (Containment)

| Инцидент | Действия по сдерживанию |
|----------|------------------------|
| Компрометация секрета | 1. Ротировать секрет<br>2. Отозвать все активные сессии<br>3. Принудительный logout всех пользователей |
| Уязвимость в зависимости | 1. Приостановить развёртывания<br>2. Обновить зависимость<br>3. Провести тестирование |
| Несанкционированный доступ | 1. Отозвать токены пользователя<br>2. Заблокировать IP злоумышленника<br>3. Проверить логи доступа |
| DDoS атака | 1. Включить ужесточённый rate limiting<br>2. Заблокировать атакующие IP на уровне reverse proxy<br>3. Масштабировать инфраструктуру |
| Утечка данных | 1. Остановить источник утечки<br>2. Определить что утекло<br>3. Уведомить пострадавших |

### Фаза 4: Ликвидация (Eradication)

```
1. Удалить вредоносный код/доступ
2. Исправить уязвимость в коде
3. Обновить зависимости
4. Изменить конфигурацию
5. Провести тестирование исправления
```

### Фаза 5: Восстановление (Recovery)

```
1. Развернуть исправленную версию
2. Проверить health endpoints
3. Восстановить нормальную работу
4. Подтвердить отсутствие проблем
```

### Фаза 6: Анализ инцидента (Post-Incident Review)

```
1. Составить хронологию событий
2. Определить корневую причину
3. Выявить пробелы в защите
4. Обновить план реагирования
5. Добавить меры предотвращения повторения
6. Обновить документацию
```

## 4. Время отклика

| Средний | 24 часа | 48 часов |

## 5. Уведомление пользователей

| Ситуация | Когда уведомлять | Способ уведомления |
|----------|------------------|-------------------|
| Компрометация аккаунта пользователя | Немедленно после подтверждения | Email, push-уведомление |
| Утечка данных пользователей | В течение 72 часов | Email,公告 на сайте |
| Плановое обслуживание | За 24 часа | Email, уведомление в приложении |
| Неплановая недоступность | В течение 1 часа | Уведомление в приложении, статус-страница |
